# Tend — Explainable Household Routine Intelligence

Tend is a privacy-first household routine-intelligence system for caretaking and home automation.

It learns a household-specific activity baseline from Ring-shaped events, detects meaningful changes across **presence, timing, and sequence**, and produces a calm, evidence-backed explanation. The deterministic analysis engine decides whether a deviation exists; Amazon Bedrock is an optional reasoning layer that explains the already-computed evidence.

## Why Tend

Traditional activity alerts are usually binary: an event happened or it did not.

Tend instead asks:

> **Is today's pattern meaningfully different from what is normal for this household?**

That distinction makes the system useful for caregiving and accessibility scenarios without turning routine changes into diagnoses or emergency claims.

## Core capabilities

- **Personalized baseline** — learns activity patterns per household over a rolling window.
- **Three explainable signals**
  - Presence — expected activity that is missing or unexpectedly present.
  - Timing — meaningful shifts from learned activity times.
  - Sequence — changes in the normal order of zone transitions.
- **Deterministic deviation scoring** — severity is calculated by auditable rules and configurable thresholds.
- **Evidence-first reasoning** — every explanation is based on structured evidence generated by the deterministic engine.
- **Constrained Bedrock reasoning** — Bedrock explains results but cannot change the deterministic severity, invent evidence, or bypass the safety contract.
- **Feedback-driven sensitivity** — caregiver feedback can adjust signal sensitivity conservatively over time.
- **Privacy by design** — no facial recognition, biometric identification, cross-household correlation, or medical diagnosis.
- **AWS-ready runtime** — DynamoDB persistence, scheduled analysis, Bedrock integration, and SNS notification support are implemented behind explicit runtime boundaries.
- **Reproducible CI** — automated type checking, builds, tests, release-readiness checks, and AWS SAM validation.

## Architecture

```text
Ring API / Ring simulator
        |
        v
Event ingestion + normalization
        |
        v
EventStore
(In-memory for local development / DynamoDB for AWS runtime)
        |
        v
Household baseline engine
        |
        v
Deterministic deviation engine
Presence + Timing + Sequence
        |
        v
Structured evidence + fixed severity
        |
        v
Reasoning layer
  +-------------------------------+
  | Amazon Bedrock (optional)     |
  | Template fallback             |
  +-------------------------------+
        |
        v
Caregiver-facing explanation
        |
        v
Feedback / notification runtime
```

A key design rule is that the reasoning layer receives **structured evidence**, not the raw event stream. This keeps anomaly detection auditable and prevents a language model from becoming the source of truth for severity.

## Ring integration

Tend includes a dedicated Ring integration boundary under `src/ingestion/ring/`.

The implementation includes:

- Ring configuration and access-token handling.
- Authenticated Ring API client calls.
- Ring event normalization into the internal `TendEvent` model.
- Ring webhook handling with HMAC verification.
- Replay/staleness protection.
- Idempotent event storage.
- Defensive handling of uncertain or evolving upstream payload shapes.
- `npm run ring:check` for an honest runtime connectivity check.

The repository also includes a deterministic development simulator. It is explicitly labeled as a simulator and is not presented as a real Ring device.

**Important verification boundary:** the project has not claimed a successful live Ring API call from the development environment. The real Ring path is implemented and tested, while live connectivity depends on a supported Ring developer environment, credentials, and network access.

## Amazon Bedrock

Tend treats Bedrock as a **reasoning/explanation layer**, not an anomaly detector.

The deterministic engine calculates:

- the composite deviation score,
- the severity label,
- the supporting evidence items.

The Bedrock adapter then converts that structured result into a short, caregiver-friendly explanation.

The output contract validates that:

- severity matches the deterministic result,
- evidence references are valid,
- unsupported numbers are rejected,
- restricted wording is rejected,
- the model cannot turn the result into a diagnosis or emergency claim.

Run the runtime check with:

```bash
npm run bedrock:check
```

The repository deliberately does not claim that a live Bedrock request has succeeded from the original sandbox environment. The adapter is implemented against the AWS SDK v3 Converse interface and has dedicated tests for failure handling and fallback behavior.

## AWS runtime

The final release includes AWS infrastructure in `infra/template.yaml`.

The SAM template defines:

- **AWS Lambda** — Tend runtime.
- **Amazon API Gateway HTTP API** — health, Ring webhook, and feedback endpoints.
- **Amazon DynamoDB** — persistent normalized event/sensitivity state.
- **Amazon EventBridge Scheduler** — recurring analysis execution.
- **Amazon Bedrock** — optional constrained reasoning.
- **Amazon SNS** — optional notification delivery.
- **IAM policies** — explicitly scoped runtime permissions.
- **DynamoDB point-in-time recovery and server-side encryption**.
- CloudFormation outputs for the webhook, feedback, and health endpoints.

The infrastructure is designed so deployment requires an explicit household identifier instead of relying on a hard-coded household value.

The AWS resources are implemented and validated through infrastructure checks; live deployment remains deployment-environment dependent.

## Security and privacy model

Tend is intentionally conservative about household data.

- No secrets are hard-coded into source.
- Ring webhook signatures are verified before payload processing.
- Duplicate event/request identifiers are handled for idempotency.
- Raw Ring payloads are not passed into the reasoning layer.
- Default logging avoids credentials, tokens, HMAC secrets, and raw sensitive payloads.
- Household identity is explicit at runtime.
- AWS permissions are scoped to the resources and actions required by the runtime.
- DynamoDB protection features are enabled in the deployment template.
- No facial recognition or biometric identification.
- No cross-household data correlation.
- No medical diagnosis or emergency declaration.
